Describe the developer you need. Get evidence, not hype.

A retrieval-augmented generation (RAG) search engine over public GitHub developers. Recruiters write what they are looking for in plain English, and the system returns a short, source-cited report on the best matches.

Honest status: this page is a showcase and does not call the live search API yet. The report below is an illustrative example of the output format, using placeholder names. It is not real data about real people.

How it works

The pipeline is written by hand without LangChain, so every stage is visible and testable.

FindActive accounts from GH Archive via BigQuery, bots removed
SampleHash buckets for a reproducible pool, then stratified quotas per domain
FetchRepo lists from the GitHub API with retries and rate-limit handling
EmbedOne text document per developer, BGE-small vectors
RetrieveNearest-neighbour search in Chroma, with metadata filters
GenerateLLM writes a JSON report that must cite repositories; links come from metadata

Constraints, stated plainly

This is a learning project running on free infrastructure and a personal laptop. These limits shape what the demo can and cannot do.

Small, biased corpus

Only ~1,800 developers, drawn from accounts active in one 8-day window. The best person for your query may simply not be indexed.

Keyword-based labels

Domains are assigned by a hand-written keyword dictionary. It is audited only lightly and misfiles some people. About 46% of the sampled pool was unclassifiable.

“Relevant” is not “best”

Search measures similarity to your words. There is no quality or seniority ranking yet, so a vague query such as “best developer” returns people who sound relevant.

Dense retrieval only

No keyword (BM25) hybrid search and no reranker yet, so exact technologies such as “Tailwind” can be missed or blurred.

Thin documents

Profiles are built from repository names, descriptions, topics and languages. READMEs and bios are not ingested yet.

Public data, partial picture

Private work, employer code and offline skills are invisible. Stars favour visibility, not skill. Treat every report as a lead, not a verdict.

LLM can be wrong

The model is instructed to use only retrieved text and to cite repositories, but it can still misread. Always verify on the linked profile.

Free-tier limits

The LLM and hosting run on free plans with rate limits, cold starts and model changes. Expect slow or unavailable moments.

Repository structure

Folders follow the pipeline stages, so each part can be tested, replaced and understood on its own.

findmethecrackeddevs/
├── src/fmcd/
│   ├── ingestion/    # GH Archive, GitHub API clients (I/O only)
│   ├── processing/   # sampling, labelling, document building (pure functions)
│   ├── retrieval/    # embeddings, vector store, search
│   ├── generation/   # prompts, LLM client, report formatting
│   ├── api/          # FastAPI app, schemas, rate limiting
│   └── config.py     # all settings and paths in one place
├── frontend/         # this page and the future search UI
├── eval/             # test queries, expected results, scoring scripts
├── tests/            # unit tests mirroring src/
├── notebooks/        # exploration only, never imported by src
├── scripts/          # run_pipeline.py and one-off jobs
├── data/             # gitignored: raw, processed, vectors
├── docs/             # design decisions, limitations, ethics
├── .github/workflows/  # CI and scheduled refresh
├── Dockerfile · requirements.txt · .env.example · pyproject.toml
├── CONTRIBUTING.md · LICENSE · README.md

Ethics. This tool searches a sample of public GitHub developers, not all developers and not all good developers. It uses only public data through official sources, never exposes emails, and should not be the sole basis for any hiring decision. Anyone can ask for removal by opening an issue.
